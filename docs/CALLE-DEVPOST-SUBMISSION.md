## Text description

### The problem

Across Lebanon, the Gulf and South-East Asia, most chat-commerce orders are **cash on delivery**.
There is no payment step to prove intent, so shops get fake orders, duplicate orders, and orders the
customer simply forgot about. The standard defence is a human phoning every single order before the
kitchen starts or the courier loads. It is slow, it is the first thing skipped at peak, and skipping
it is exactly when failed deliveries cost the most — the goods are already made and already moving.

Text cannot fix this. A customer who ignored the chat will ignore a follow-up message too. The job
genuinely needs a phone call, and until now that call needed a person.

### What we built

FrontDesk is a multi-tenant AI front desk: a business connects its WhatsApp, Messenger and Instagram
accounts, loads its catalogue, hours and policies, and an AI assistant answers customers around the
clock, captures orders and bookings, and hands off to a shared human inbox.

**Phone Follow-Through** is the new layer. When a record needs closing, the same AI that has been
chatting **picks up the phone through CALL-E**:

| Trigger | What the call does | What happens to the record |
|---|---|---|
| A cash-on-delivery order lands — one click on the Orders page, or automatically N minutes later | Greets, reads back the real items and total, confirms the delivery address, records any change the customer asks for | order → `confirmed` / `cancelled`, or `needs_review` for a human |
| A booking | Asks whether the customer can still attend, captures a requested new time without promising it | booking → `confirmed` / `cancelled`, or `needs_review` |
| Any conversation — an operator types a goal | Whatever the team asks, grounded in the business identity | an internal note in that conversation, no record mutation |

The result is not a transcript dumped in a log. It is a schema-validated JSON object that moves the
order, posts a readable note in the customer's own chat thread, raises a notification, and fires the
tenant's outbound webhook — so the phone call becomes a first-class event in the same system the
chat already lives in.

### Why this is not "an AI that makes phone calls"

Three things make it specific rather than generic:

1. **The call is briefed from the database, not from the chat.** The spoken instruction is compiled
   from the actual order rows, the stored delivery address, the tenant's delivery policy, its legal
   name and its configured language. The chatbot's own sentences are never the source. This matters:
   a model summarising a conversation will confidently read back an item the customer never ordered.
2. **It is escalation, not outreach.** Text first; voice only when a record is stuck. Nothing is
   cold-called. The phone number comes from the order the customer placed.
3. **The result is governed.** An order only moves on `task_completed` **and** completion confidence
   ≥ 0.7 **and** an unambiguous disposition. Anything else — voicemail, no answer, a hesitant
   "maybe", schema drift — becomes `needs_review` and waits for a human. Low confidence can never
   cancel someone's dinner.

### How CALL-E is used at runtime

- **SDK `@call-e/calle` v0.7.0**, imported in exactly one file, `apps/api/src/lib/calle.ts`.
  Everything else in the codebase goes through that wrapper.
- Calls are created with `client.calls.create({ task, recipients: [{ phones, region, locale }],
  resultSchema, recipientResultSchema, metadata }, { idempotencyKey })`. The per-kind
  `result_schema` is generated by the task builder, so CALL-E validates the extraction for us.
- Terminal results arrive **two ways that converge on one compare-and-set**:
  a public webhook receiver `POST /api/v1/calle/webhook/:orgId?token=…`, which deduplicates on the
  `CALL-E-Event-Id` header and then **re-reads the call from `client.calls.get`** rather than
  trusting the delivered body; and a 30-second poll in the API process for deployments without a
  public URL. Either can win; neither can double-apply.
- `completionConfidence`, `taskCompleted`, `summary`, `structuredResult` and the per-attempt
  `transcriptTurns` are all persisted and surfaced in the portal.

### Safety, enforced in code rather than documentation

- `CALLE_DRY_RUN=true` is the **committed default**. Every code path runs — task row, idempotency
  key, status machine, order flip, inbox note, notification, webhook — but nothing is dialed: the
  task "rings" for 15 seconds then completes with a synthetic result derived from its own schema,
  labelled DRY RUN everywhere it appears. The whole feature is reviewable with no credentials.
- `CALLE_LIVE_OVERRIDE_PHONE` redirects **every** live call to one verified number, and records the
  substitution in the call metadata. A demo cannot dial a real customer by accident.
- Contacts who opted out or are blocked are refused before a task row exists.
- Numbers outside CALL-E's 23 supported countries are rejected up front with a clear error, rather
  than failing mid-call.
- A per-tenant daily cap plus a delay after the order lands bound both spend and annoyance.
- Every task persists a durable `Idempotency-Key` **before** the first request, so a crash or a
  network retry can never place a second call.

### Multi-tenancy

Phone tasks are a tenant-scoped table protected by Postgres row-level security, like every other
table in the platform, and the cross-tenant isolation test that blocks deploys was extended to cover
it. One deployment serves many businesses; one business's transcripts are invisible to another's.

### What was built during the submission period

The repository predates the hackathon as a chat-only AI front desk. Everything phone-related is new
work created on **14 September 2026**, during the submission period:

- a new `phone_tasks` table and migration (with row-level security applied inline), plus a
  per-tenant settings column;
- `lib/calle.ts` — the CALL-E wrapper with the dry-run, override, region and idempotency rails;
- `lib/phone-tasks.ts` — the three task builders and the governed write-back;
- `lib/phone-task-tick.ts` — the polling and auto-confirm scheduler;
- the portal routes and the public CALL-E webhook receiver;
- a new Phone tasks page, a Confirm-by-phone action on Orders and Bookings, and a Call-customer
  action in the inbox;
- the shared Zod contract, the new feature flag, the error codes, the tenant-isolation test block
  and the documentation.

(The repository was also separated from its original single-brand codebase into a brand-neutral core
on 29 August 2026, likewise inside the submission window.)

### Testing instructions for judges

The public repository is <https://github.com/TayseerLaz/frontdesk-core>. No CALL-E credentials are
needed to exercise the feature end to end, because dry-run is the default.

```bash
git clone https://github.com/TayseerLaz/frontdesk-core.git
cd frontdesk-core
cp .env.example .env     # fill DATABASE_URL, REDIS_URL, both JWT secrets, BRAND_*, INITIAL_ADMIN_*
docker compose up -d     # postgres + redis (or point at your own)
pnpm install
pnpm bootstrap           # migrate + create the first admin
pnpm dev                 # portal http://localhost:3000/app, API http://localhost:4000
```

Sign in with `INITIAL_ADMIN_EMAIL` / `INITIAL_ADMIN_PASSWORD`, open **Orders**, create an order, and
click **Confirm by phone**. Watch **Phone tasks**: the task completes in about 15 seconds, the order
flips, and the structured result plus transcript appear in the drawer.

To place real calls, set `CALLE_API_KEY`, `CALLE_DRY_RUN=false`, and keep
`CALLE_LIVE_OVERRIDE_PHONE` pointed at a number you control.

### What comes next

Abandoned-cart callbacks, supplier stock checks before confirming an order, delivery-window
renegotiation when a courier slips, and a per-tenant voice persona that matches the chat persona.
